# Muslim Plus Android phone-test fixes

This is a sideload acceptance candidate. The existing app ID is `com.muslimplus.app` and the build version is 1.0.3 (4). The acceptance APK uses the debug certificate and a device-test web bundle. Production backend, OAuth and VersionHub settings are required separately for a production web bundle, and release signing is required for a distribution APK. No deployment or store action took place.

**Fixed** means the code was changed. **Verified** identifies checks actually run and their scope. **Still Pending** identifies checks that need hardware, live services or production configuration.

| Area | Root cause and change | Status |
| --- | --- | --- |
| Location setup | A reverse lookup failure used raw coordinates as the visible label. On Android the platform geocoder now tries to resolve the name, with the existing online lookup as a fallback and a readable “Current location” label if neither has a name. Previously saved coordinate labels remain usable and display a readable label. Onboarding and Prayer Settings used different search providers, had different result limits, and did not expose every failure state. They now use one debounced, time-bounded city picker with region, loading, no results, error and retry. Results keep their selected coordinates. Raw provider error codes are kept out of UI copy. | **Fixed.** **Verified.** mocked precise, approximate and denied branches, native and online name selection, legacy labels, manual results and retry. **Still Pending.** native permission dialogs, real city coverage, GPS quality and location services on Samsung and Huawei. |
| Home | Loading flags hid valid cached prayer data and a fetch failure fell through to an endless “Calculating…” placeholder. A stale phone-location request could also override a manual selection. The card keeps valid data visible while it refreshes, reports a failed or missing schedule with retry, and opens the city picker directly. The phone location action explains that it refreshes prayer times and saves the location used by Qibla. Columns wrap rather than crowding the countdown. | **Fixed.** **Verified.** fixture-backed browser onboarding → Home, service failure/retry, countdown, changed location and responsive layout. **Still Pending.** live schedule and next prayer after an actual APK install. The AlAdhan request timed out from this machine. |
| Qibla | Android drove heading from a GPS watch at one-second intervals and treated GPS errors as compass errors. The JS angle also wrapped at north before reaching the CSS animation. Android now uses rotation-vector sensors with a geomagnetic or accelerometer/magnetometer fallback, screen rotation remapping, declination correction and activity pause/resume handling. Continuous angular smoothing crosses north by the shortest path. The rotating compass orbit no longer contributes a square overflow area on narrow screens. The screen distinguishes missing readings, phone tilt and low calibration, with a bearing from true north and a retry when readings are missing. | **Fixed.** **Verified.** heading math, browser route with simulated heading and Android compilation. **Still Pending.** native heading accuracy, settling, background/resume, screen rotation, calibration, sensor-less devices and OEM behavior. |
| Quran | The sticky bar had speed pills that crowded narrow layouts, no media progress and no seeking. The end handler automatically navigated before showing a completion choice. Surah and Juz now use a compact bar with reciter, pause/play, elapsed and remaining time, and seeking within the current ayah. Surah offers previous/next and a completion panel. Automatic next-Surah playback remains available as an explicit reader setting. The reader releases its audio element on route changes and close. During QA, a timed autoplay handoff reproduced a track readiness race. Autoplay now starts after the new reader registers its audio listeners. Existing reciters, recording URLs and Bismillah rules are retained. | **Fixed.** **Verified.** simulated media controls, time updates, seeking, completion and one active audio element across navigation. **Still Pending.** audible playback, real CDN behavior, switching reciters mid-play and interruption/resume on the APK. |
| Tasbih | The fixed-height, overflow-hidden screen forced fixed-size controls and large cards into the same space. The screen can grow on short displays, the dhikr card and bead ring are more compact, and the counting and swipe hint remains visible. Existing counting and themes remain in place. | **Fixed.** **Verified.** browser route and layout at the dimensions below. **Still Pending.** physical touch, swipe and visual review across OEMs. |
| Duas | Nested elevated white rows repeated at each level and large paddings reduced reading width. Categories now use a quieter surface, titles read as rows, and expanded text gets a contrasting reading surface with responsive Arabic, transliteration and translation spacing. | **Fixed.** **Verified.** route and layout at the dimensions below. **Still Pending.** physical-device visual review, large Android font setting and live share/audio. |
| Islamic calendar | The grid trusted API row order, only showed the first Gregorian month, and used strict comparisons of differently typed date fields. It now validates a complete 29/30-day month, sorts by numeric Gregorian dates, aligns the first cell to its UTC weekday, labels Hijri and Gregorian order, and shows both Gregorian months when needed. Month navigation resets stale selection and retries the intended month. The provider conversion method is retained. | **Fixed.** **Verified.** reversed rows, date validation, weekday alignment, Gregorian/Hijri year boundaries and month navigation with fixtures. **Still Pending.** live provider response and any local moon-sighting differences. |
| Responsive Android UI | Fixed card and control sizes compounded WebView width and text differences. Scoped changes allow labels and columns to wrap, cap scrollable location sheets and add safe-area spacing to the audio player. | **Fixed.** **Verified.** headless mobile viewport coverage as listed below. **Still Pending.** Android WebView/OEM comparison, edge insets and system font scaling on Samsung and Huawei. |
| Zakath Ledger | The More tile still shows Coming Soon and stays on More. Ledger UI, calculations, APIs and data were outside the edits. | **Verified.** Coming Soon navigation and isolated financial regressions. The original SQLite SHA-256 matched before and after. |

## Reproduction and automated verification

The old location fallback was directly encoded in the original tests as a numeric label. The Home failure path was traced to the prayer fetch error and the previous card branch, and the live AlAdhan request timed out. Android Qibla's GPS-driven update and fallback paths, the Quran player's layout and end behavior, the fixed Tasbih viewport and the Calendar sort assumptions were confirmed from the pre-change source. These source-level reproductions do not substitute for replaying the original OEM failures.

- The JavaScript suite had **153 passes and 0 skips**, including the isolated Django integration, active-route renders and added location, compass and calendar regressions. The project dependencies require the matching ARM Node/esbuild pair on this Mac.
- The Django suite had **27 passes** via `manage.py test api` using isolated test storage. The original `backend/db.sqlite3` SHA-256 is `4aa2aa74377e869129c246cc5f29d090479d2024da1e98247dd865291687fee0`.
- Headless Chromium checked the packaged web assets at **320×568 (130% root text), 412×915 (100%) and 600×360 (120%)**. Home, Qibla, Tasbih, Duas, the Quran audio bar and the calendar grid stayed within the test viewports. The fixture also exercised manual location onboarding, prayer retry and countdown, Quran seeking and adjacent Surahs, sorted dates and year rollover, and Ledger Coming Soon. Qibla was checked at eight simulated headings per viewport. The browser run recorded no uncaught JavaScript exceptions.
- Requests to AlAdhan, Open-Meteo and the existing Quran audio CDN timed out from this machine. The browser checks used synthetic network, geolocation and media responses, with no real account or coordinates submitted.
- The migration rehearsal **passed** against a temporary SQLite backup. All three existing rows matched through forward, rollback and reapply. The source was opened read-only and its digest stayed the same.
- Clean Android app builds passed for debug and release. The debug and release Android unit tests each passed. The instrumentation APK compiled. Instrumentation was not executed. Debug and release lint each reported **0 errors, 22 warnings**, with no findings in the two changed native location/compass plugins. Debug lint needed one AndroidX dependency from official Google Maven, supplied to the temporary Gradle build. The Android release output is unsigned.
- ADB listed no attached Android devices. The installed x86_64 AVD failed at Hypervisor.Framework initialization (`HVF 0x4 / Invalid argument`). No emulator install, native sensor readings or physical verification is claimed.

Verification files are in [build/android/verification](build/android/verification). The folder includes the JavaScript and Django results, Android build and lint reports, browser fixture scripts and results, the APK signature, and SHA-256 checks. The APK signature was validated locally without installing it on a phone.
