# Muslim Plus final candidate retest guide

Run the checks below on the approved, signed Android and iOS acceptance builds under `com.muslimplus.app`. The unsigned device-test outputs in the release report are compilation evidence. Wait for compatible signed builds and an authorized staging setup before starting candidate sign-off. Use spare devices or disposable app data for resets and destructive account tests.

Record one row per check. Include the platform, device model and OS, app version/build, artifact SHA-256 or distribution build reference, install method, date/time and time zone, network, permissions, expected and actual result, and a redacted screenshot or log if it fails. Use **Pass**, **Fail**, **Blocked**, or **Not run**. For an upgrade, record the previous build and signing lineage too.

| Check | How to run it | Pass condition |
| --- | --- | --- |
| 1. Install, upgrade and scope | On a spare phone, install the signed build and launch it. Separately install over a compatible signed prior build with disposable bookmarks, preferences and progress. Relaunch after closing the app. Tap the Zakath Ledger tile in More. | Launch and onboarding work. The compatible upgrade retains the sample data. The tile says **Coming Soon** and stays in normal navigation. If the installer reports a signature mismatch, record it and preserve the existing installation. |
| 2. Quran index failure and Retry | Open Quran on a working network and confirm the Surah and Juz lists. Leave the screen. Disconnect the phone, reopen Quran and wait for the error. Reconnect and tap **Retry**. Repeat in Malayalam. For HTTP 503, invalid JSON/schema and a body that stalls, use an approved QA network harness or proxy capable of injecting those faults. | Error and Retry appear in the selected language. For a stalled response, the loading attempt ends at about 10 seconds. Retry restores the lists without restarting the app and search/navigation work again. Record fault cases as blocked if the harness cannot inject them safely. Keep platform TLS checks enabled. |
| 3. Location permission and Qibla | Deny location, choose a city manually, then grant location and try phone location. Revoke location from system settings and reopen. On Android test approximate and precise grants. For Qibla, compare the live reading and north-up bearing against a trusted reference in a known place away from metal. Rotate the phone and verify alignment feedback. | The app explains denial, offers manual city, and refreshes with the chosen location and time zone. Compass response follows rotation, bearing matches the reference within the team's agreed tolerance, and low-confidence readings are clearly indicated. Record actual headings and any OEM variation. |
| 4. Actual scheduled Adhan | Verify automatic device date/time and the selected city, Madhab, and time zone. Record the next prayer shown in the app and its timestamp. Enable prayer notifications and Adhan sound, set a usable volume and temporarily disable Focus/silent restrictions for the baseline. Lock the phone before the displayed prayer time and record the actual delivery timestamp with another device. Repeat with the app in the background. | Alert and sound occur once at the time shown in the app, within the acceptance tolerance agreed before testing. Record the exact delay. Treat a mosque timetable difference separately from delivery delay. A short diagnostic alarm does not count. |
| 5. Android Adhan permissions and Stop | Deny/revoke notification and exact alarm access, check the message, then re-grant and schedule another actual prayer. At delivery, tap **Stop Adhan** and check that the next prayer stays scheduled. Repeat after reboot and with the intended battery setting. | Permission changes have clear feedback. With both grants, the full sound starts and Stop ends playback without cancelling later alarms. Reboot and battery settings behave as recorded. Document force-stop separately from backgrounding. |
| 6. iOS alert and action | Deny, grant and revoke notifications from iOS Settings. On the baseline scheduled alert, listen for the short Adhan and tap **Open prayer times** from the notification. Repeat with Focus/silent restrictions and record those settings. | With permission and sound allowed, the short alert plays and the action opens Prayer Times. Record OS restrictions separately. The supported iOS alert is about 25 seconds. |
| 7. Reminder interaction and time changes | Enable prayer, Daily Ayah, calendar and Ratheeb reminders. Change the selected city or prayer settings, complete a prayer and reopen after losing and restoring connectivity. Check pending alerts with approved tooling if available. Use a spare device for reboot and a time zone or date boundary test. | Future prayer times are refreshed. Unrelated reminders persist and the completed follow-up clears. There are no duplicates. Verify the documented seven-day renewal limit by reopening online before expiry. |
| 8. Account and data lifecycle | Only if the approved account scope includes these flows, use a disposable account and records in isolated managed staging. Verify Google callback, logout and cross-account isolation. Run the separate backend concurrency gate in the final report. Exercise deletion, lost-response retry, and post-deletion relaunch with disposable data only. | A stale session cannot save. An already committed save is removed by deletion. A repeated deletion receipt is safe, device cleanup completes, and unrelated accounts retain their data. Never open Ledger to create test records. Use an approved staging test client. |
| 9. VersionHub and final smoke | Use authorized staging VersionHub records for both IDs and build numbers. Exercise no update, optional dismissal, mandatory behaviour and recovery when offline. Confirm the correct platform link only if an approved destination already exists. Check Home, prayer/calendar, Quran detail playback and language after reconnect. | Correct platform policy and URL, no false blocks, and key screens recover. Record production store link and in-app review validation separately when authorized. |

A signed build can pass only with observed results for the exact artifact. Any change to the source, embedded configuration, signing or build number requires a new artifact hash and targeted retest. No deployment or store submission is part of this guide.
