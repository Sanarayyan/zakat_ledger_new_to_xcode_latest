# Muslim Plus Android Gradle security advisory triage

10 November 2026. **The four target findings have a controlled buildscript remediation. Production signing remains gated by unapproved conditional findings and final release acceptance.** The table covers all **48 unique advisories**, **49 package/advisory matches** and **12 affected Maven coordinates** from the frozen release inventory. The duplicated advisory is GHSA-f6hv-jmp6-3vwv, which affects both HTTP codec modules.

Muslim Plus uses Gradle and the Android Gradle Plugin to assemble and package its Android app. This review assumes a controlled signing worker with access to release keys and potentially untrusted dependency, archive or network inputs. Actual production CI, signing credentials, proxy configuration and build-input trust policies were unavailable.

## Controlled remediation results — 10 November 2026

**The four target findings are remediated in the controlled build configuration.** The three-family patch removes their affected-version matches. A direct Jetifier consumer probe still expands an external entity with JDOM 2.0.6.1, so a version-only fix was insufficient. The root buildscript now rejects attempts to enable Jetifier. The negative configuration test with `-Pandroid.enableJetifier=true` failed at the guard with the expected security message. The existing AndroidX build path runs with Jetifier disabled. Ordinary XML parsing, BC certificate/keystore initialization and a gRPC/Netty HTTP/2 request passed their compatibility probes.

### Applied scope and compatibility

The only implementation edit is `android/build.gradle`. It rejects `android.enableJetifier=true`, adds Netty's **4.1.140.Final** BOM to the buildscript classpath and dependency constraints for JDOM **2.0.6.1** and Bouncy Castle **bcprov/bcpkix/bcutil-jdk18on 1.85**. AGP **8.13.0**, Google Services **4.4.4**, Gradle **8.14.3**, JDK **21**, app dependencies and `com.muslimplus.app` retain their baseline values. Guava, Commons Compress and jose4j remain at their original versions because their remediation was outside the approved four findings.

The BOM aligns all **11** resolved Netty modules. The BC constraints align its **three** modules. Together with JDOM, **15** existing buildscript coordinates change version, and the Netty BOM adds one platform coordinate. Both app graphs compare exactly with the frozen baseline, with **77 runtime** and **38 compile** coordinates. The buildscript inventory grows from **129 to 130**, and the union from **205 to 206** coordinates. All **510 other frozen source files** match the baseline manifest.

Compatibility risks identified before editing included gRPC 1.69.1 integration with newer Netty TLS/HTTP/2 handling, BC certificate/provider changes between 1.79 and 1.85, and Jetifier XML behaviour. Staying on Netty 4.1 and the same BC artifact family avoids major API migrations. An intentional compatibility restriction now rejects the legacy Jetifier transform. The inspected dependencies use AndroidX and the baseline did not enable Jetifier. If a future dependency requires Jetifier, stop and reassess that workflow rather than removing the guard. The local validation below checks those specific consumers. The actual production keychain, TLS configuration and signing operation remain outside the checked scope.

### Local verification

GRADLE_REMEDIATION_CHECKS

The Jetifier security probe calls its real `XmlUtils.Companion.createDocumentFromByteArray` method with XML referencing a disposable local marker file. The marker appears in the parsed text under patched JDOM. The probe also parses ordinary XML successfully. This demonstrates unsafe behaviour if that consumer is reached, without demonstrating that the ordinary release task activates Jetifier. The project does not explicitly enable Jetifier. The isolated compatibility harness exits **2** to retain the security failure in evidence.

This result changes the original version-only recommendation. JDOM 2.0.6.1 passes the registry affected-range check, but its Jetifier consumer remains unsafe when invoked directly. The buildscript guard enforces the supported release configuration and stops configuration before app tasks when Jetifier is requested. Keep the guard in the frozen source and CI. The direct-parser probe remains a documented failing positive control, not a claim that the library now hardens all XML callers. Any new direct Jetifier invocation, custom XML task or requirement to enable Jetifier needs a new security review.

### Packaged application check

The unsigned APK SHA-256 is `6987bdffe9a7f804c40557ee301007d456619623d671a613867e2a7046605f83`. The unsigned AAB SHA-256 is `2e5ae17b0f0f1cd83f86719d6286514d172ec2ef3e9b23ab5676efc9961b0e4f`. Both are the official-ID device-test diagnostic outputs from final candidate preparation.

All DEX files were inspected with Android SDK dexdump. Each artifact has **9,012 class definitions** across two DEX files. The vulnerable Netty, JDOM, jose4j, Commons Compress and Bouncy Castle packages are absent. Under `com/google/common/`, only `ListenableFuture` is present, supplied by the distinct runtime coordinate `com.google.guava:listenablefuture:1.0`. The vulnerable Guava collection classes and their deserialization methods are absent. There are no embedded JAR, AAR or native SO payloads in either artifact. This supports application-runtime non-applicability for all 48 findings. Recheck the final signed, production-configured outputs.

### Build consumer checks

Bytecode inspection found Jetifier's `XmlUtils.Companion.createDocumentFromByteArray` constructing `SAXBuilder` and calling `build(InputStream)` without local entity-disabling calls. The project does not explicitly enable `android.enableJetifier`, and actual transformation on the production signer has not been observed. Removing JDOM from the shipped-app risk list does not close this build-worker input concern.

Bundletool 1.18.1 references jose4j from code-transparency signature helpers. No `JsonWebEncryption` reference was found in that JAR, which supports a conditional exception for the compressed-JWE advisory. It is not a complete reflective or external-plugin call analysis.

The inspected gRPC Netty JAR references proxy handlers and SSL context configuration. It has no direct `SniHandler` or `HttpContentDecompressor` reference. The checked graph has no netty-tcnative coordinate. Actual TLS provider selection, remote test listener binding, custom trust managers and system-provided native libraries remain runner checks.

The sdk-common JAR references Bouncy Castle through `KeystoreHelper`. No direct GOST CTR, FrodoKEM or LDAPStoreHelper reference was found there. Certificates, ASN.1 data and provider selection on the signing worker require a narrower production-path assessment before waiving their gates.
